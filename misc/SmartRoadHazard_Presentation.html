What makes it different

Three decisions that actually matter

01

Depth classification

The ultrasonic sensor measures how far the road surface drops relative to a rolling baseline. Distance delta above 25 cm = deep pothole. 8-15 cm = speedbreaker. Shallow and medium in between. Objective depth, not a guess.

Why it matters: repairs can be prioritized by severity, not just location.

02

Crowd verification

A hazard only gets published after 3 independent vehicles detect it within a 15-metre radius (Haversine). One vehicle hitting a bump doesn't trigger alerts. Three independent detections does. The system self-validates without any human in the loop.

Why it matters: alert fatigue is the main reason drivers stop trusting hazard apps.

03

Shadow alerts

When a medium or deep pothole is verified, the dashboard fires a warning banner that auto-dismisses in 5 seconds. This specifically helps drivers behind large trucks and buses who can't see the road surface ahead of them.

Why it matters: the most dangerous potholes are the ones you can't see coming.

Hardware layer

The sensor setup

Simulated entirely in Wokwi — no physical hardware needed to run or test the system. The ESP32 runs the same firmware it would on a real vehicle mount.

Components

ESP32 microcontroller
HC-SR04 ultrasonic sensor
SSD1306 OLED display
3 status LEDs (R/G/B)

Trigger: GPIO 5 · Echo: GPIO 18. The first 10 readings set the baseline distance. Everything after is measured as a delta against that baseline.

Classification logic

delta > 25 cm  → DEEP POTHOLE
delta 15-25 cm → MEDIUM POTHOLE
delta 5-15 cm  → SHALLOW POTHOLE
delta -5 to -15 → SPEED BREAKER
| delta | < 5 cm → CLEAR ROAD

Backend

Where the verification logic lives

Three Python files. The crowd verification in database.py is the core of the whole system.

bridge.py

Data bridge

Reads serial output from ESP32 (or generates realistic Nagpur route data in demo mode). Pushes detections to the Flask API and Firebase simultaneously.

database.py

Verification engine

Every new detection runs add_detection(). It checks all existing records within 15 metres (Haversine). If count reaches 3, verified flips to 1. That's the entire algorithm.

1 / 3 detections — unverified

server.py

REST API

Five endpoints over Flask with full CORS. The two most used: GET /api/hazards (verified only) and POST /api/hazards (submit detection).

Deployed: Render · Port 5001

Frontend

The live map dashboard

Runs entirely in the browser. No app install. No API key. No billing account. Leaflet.js on OpenStreetMap tiles — free, fast, and deployable on Vercel in under a minute.

What the map shows

Grey marker — 1 or 2 detections, not yet confirmed
Yellow — shallow pothole (verified)
Orange — medium pothole, shadow alert fires
Red — deep pothole, highest priority alert
Blue — speed breaker

Live sync

Two modes: Firebase listener (instant push) and local polling every 2 seconds. Both work. Firebase mode keeps all open browser tabs in sync without anyone refreshing.

Shadow alert bar

A warning banner slides in from the bottom when a medium or deep hazard is verified nearby. It auto-dismisses in 5 seconds — enough time to slow down, not long enough to be annoying.

Tooltip detail

Hover any marker: type, severity, and verification count (e.g. "2/3 verified" or "✓ Verified").

Challenges

Three walls we actually hit

None of these were theoretical. Each one blocked progress and required a real fix.

🚧
macOS blocked port 5000

AirPlay Receiver on macOS Monterey silently occupies port 5000. Flask's default port. The app would start, appear to work, and then randomly fail to serve requests. Moved to port 5001. The lesson: when something works in CI and fails on a dev machine, check what else is running on that port.

🗺
Google Maps requires a billing account

The original design used Google Maps. Midway through, a billing account was required even for free-tier usage. Switched to Leaflet.js and OpenStreetMap tiles. No key, no account, no surprises. This also made the project deployable by anyone without setup steps.

⚡
Wokwi serial output too fast to demo live

When the ESP32 simulation runs at full speed, the serial data floods the bridge faster than a live demo can follow. Built simulator.py — a keyboard-driven interface where pressing 1-4 fires specific hazard types on demand. Better than the real thing for presentations.

Conclusion

What we built, and why it's different

Most road hazard detection systems either need a human to file a report or accept every sensor reading as ground truth. This system does neither. It collects sensor data automatically and only acts when three independent vehicles agree on the same hazard within 15 metres. That one design decision — crowd verification before alerting — is what keeps it usable on real roads.
