Core workflow

From login to live impact data in 4 steps

This is the loop a coordinator runs every time an event goes live — the dashboard updates in real time as each step happens.

1

Sign in and land on the dashboard. The mini calendar shows today's events. Animated stat cards show total events, active volunteers, completion rate, and upcoming events this week.

2

Staff creates an event. Category, capacity, location, datetime, cover photo, enrollment type (open or assigned). Status starts as Planned and auto-flips to Ongoing at start time.

3

Volunteers join. Open events show a join button. Assigned events show a staff-managed attendee list. Join requests go through an approval flow — pending, approved, rejected — with rejection notes.

4

Event completes. Analytics update live — donut charts, bar charts, volunteer trend lines. The Reports page gives the full picture across all events, staff, and months.

Key features

Six modules. One coherent system.

🗓

Smart calendar

Month, week, and agenda views. Color-coded categories with auto contrast. Click any day to create an event (admin/staff). Export to shared Google Calendar.

🔐

Role-based access

Four roles: Admin, Staff, Volunteer, Viewer. Custom Firebase claims enforced on both frontend routes and backend endpoints. No role leakage.

📈

Impact analytics

Donut charts (status/category), bar chart (monthly events), 6-month volunteer participation line chart, staff productivity table — all live from Firestore.

🔔

Smart notifications

Push (FCM) + email (Resend) reminders at 24h, 6h, and 3h before each event. Idempotency tracking prevents duplicate reminders. Per-user preference settings.

👤

Enrollment workflows

Two modes: open (volunteers apply, staff approve) and assigned (direct staff assignment). Capacity validation, duplicate prevention, rejection notes included.

📸

Photo documentation

Upload event photos stored in Supabase. Metadata includes uploader identity and caption. Photos are attached per event for audit and reporting purposes.

Access model

Four roles that mirror how NGOs actually work

Most productivity tools bolt on sharing after the fact. Trackly's permission model was built from the org chart up — admins, field coordinators, volunteers, and read-only stakeholders each get exactly what they need.

RoleWhat they can doReal-world equivalent
Admin Create/delete events, manage user roles, delete users, view all analytics and reports Program director or NGO head
Staff Create and edit events, manage attendees, assign volunteers, upload photos Field coordinator or program manager
Volunteer Browse open events, submit join requests, view personal event history, upload photos Volunteer or field worker
Viewer Read-only access to events and schedules — no creation or enrollment actions Donor, board member, or external stakeholder

Roles use custom Firebase claims synced to Firestore. Both the frontend routes and the Flask API independently verify permissions — if one check fails, access is denied.

Decision 1

Firestore real-time listeners

The dashboard uses onSnapshot so every connected client sees event status changes immediately — no polling, no refresh needed.

Decision 2

Dual permission enforcement

Roles are verified at the React route level and in the Flask API via Bearer tokens. A compromised frontend still can't reach protected data.

Decision 3

Supabase for file storage

Event photos go to Supabase rather than Firebase Storage to separate file costs from database costs and avoid Firestore document size limits.

Under the hood

Three problems that actually took work to solve

01

Auto-status transitions

Events flip from Planned → Ongoing → Completed automatically based on start and end times. The logic runs in useEvents.ts on every fetch and normalises all Firestore Timestamps, JS Date objects, and Unix epoch values through one utility before comparison.

Without this, an event that started at noon would still show "Planned" until someone manually changed it.

02

IST timezone normalisation

Firestore stores all times in UTC. Without normalisation, Indian users were seeing events appear a day early or late in the calendar. Built toIST(), nowInIST(), and todayInIST() utilities that every date display passes through.

This is the kind of bug that's invisible in development and surfaces the moment a real user in a real timezone tries the app.

03

Reminder idempotency

The notification scheduler runs on a cron to send reminders at 24h, 6h, and 3h before each event. Without idempotency tracking, the same reminder would fire on every scheduler run. Added a Firestore flag per reminder per event that gets checked before any message is sent.

A ±90 minute window handles schedule drift — if the cron runs slightly late, the reminder still fires.

Notification system

Reminders that reach people where they actually are

Email alone isn't enough for volunteers in the field. Push alone doesn't work for people who don't install apps. Trackly sends both, intelligently, without duplicating.

Building it

What took longer than expected, and what we learned

01

Firestore Timestamp hell

Firestore returns Timestamp objects. Some parts of the code expected JS Date objects. Some expected Unix milliseconds. The same event time came in three different shapes depending on how it was stored. Built a single normalisation utility that every date comparison routes through.

Lesson: normalise data at the boundary, not at the point of use.

02

CORS on Render's dynamic URLs

Render generates preview URLs for each deployment that change with every push. The Flask CORS config originally used a hardcoded whitelist, which broke every time the Vercel frontend URL changed. Rewrote CORS handling to dynamically allow any *.vercel.app origin.

Lesson: never hardcode deployment URLs in CORS config during active development.

03

Real-time + TanStack Query conflict

TanStack Query is built for HTTP requests with clear cache invalidation. Firestore's onSnapshot is a push model. Running both on the same data caused stale data and double renders. Resolved by separating real-time subscriptions from Query-managed endpoints with explicit cache invalidation hooks.

Lesson: pick one data model per data domain and stick to it.

What comes next

Trackly works. Here's where it goes from here.

The core loop is solid. These three additions would take it from a strong student project to something an NGO would actually deploy for their full team.

Near term

Bulk CSV event import

NGOs with existing event schedules in Excel should be able to onboard in minutes, not hours. Drag-and-drop CSV upload with field mapping and validation preview.

Solves the biggest onboarding friction point for organisations with historical data.

Mid term

SMS via Twilio

Push and email don't reach volunteers in areas with poor connectivity or volunteers who don't use smartphones. SMS does. Twilio integration would extend the notification stack without changing the existing scheduler logic.

Particularly relevant for rural NGO operations in India.

Research track

QR attendance scanning

Replace manual check-in lists with a QR code per event that volunteers scan on arrival. Works offline on the coordinator's device and syncs to Firestore when connectivity returns.

Field events often have poor internet — offline-first is the right design target here.
